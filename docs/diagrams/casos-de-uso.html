Quién puede hacer qué en el sistema

A diferencia del diagrama anterior (que mostraba tablas de datos), este es un diagrama de casos de uso de verdad: no muestra código ni base de datos, sino actores (los tipos de usuario) y las acciones que cada uno puede realizar en la aplicación. Se construyó a partir del control de acceso real definido en components/dashboard/sidebar.tsx y lib/supabase/middleware.ts, no de una suposición genérica.

Tres ideas de UML que vale la pena fijar aquí

Generalización (la línea sólida con punta hueca): Admin, Profesor, Acudiente y Estudiante no repiten "puede ver su inicio, puede editar su perfil" cada uno por separado — todos heredan ese comportamiento de un actor abstracto común, "Usuario autenticado". Es la misma idea de reutilización que ves en código al no repetir lógica.

«include» (flecha punteada, siempre obligatoria): "Ver panel de inicio" siempre incluye "Iniciar sesión" como paso previo — no se puede dar el primero sin el segundo. Refleja el guard real en proxy.ts, que redirige a cualquiera sin sesión antes de llegar al dashboard.

«extend» (flecha punteada, opcional): "Vincular cuenta automática" extiende "Registrarse" pero solo ocurre a veces — cuando el documento ingresado ya existía en estudiantes/acudientes. Si no hay coincidencia, el registro ocurre igual, simplemente sin ese paso extra.

Un mismo caso de uso, dos actores, dos resultados (novedad): tanto Admin como Acudiente llegan a "Crear matrícula" — es la misma acción del sistema — pero la matrícula que resulta no es igual: la de Admin nace Activa, la de Acudiente nace Pendiente y no cuenta como cupo ocupado hasta que Admin la mueve a Activa en "Cambiar estado de matrícula". El diagrama de casos de uso no separa esto en dos ovalos porque, para el negocio, sigue siendo una capacidad ("puedo registrar una matrícula") — la diferencia de permisos vive en el código (crearMatricula vs. crearSolicitudMatricula en lib/actions/matriculas.ts), no en el modelo de casos de uso.

Este diagrama describe capacidades (qué puede iniciar cada actor), no la base de datos. Para ver qué tablas y columnas hay detrás de cada caso de uso, ese es el otro diagrama (entidad-relación) que ya vimos — los dos se complementan: uno explica el quién y para qué, el otro el qué se guarda.
