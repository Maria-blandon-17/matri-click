Cómo viaja un dato dentro del sistema

Los otros tres diagramas describen estructura (qué tablas hay) y permisos (quién puede hacer qué). Este es distinto: sigue el recorrido real de un dato — desde que haces clic en un botón hasta que la pantalla se actualiza — cruzando las tres capas reales del proyecto: el navegador, el servidor de Next.js, y Supabase.

Las tres capas

Navegador

Client Components ("use client"): formularios, botones, tablas con paginación. No hablan con la base de datos directamente — nunca tienen la llave secreta.

Servidor Next.js

proxy.ts (guarda de sesión), Server Components (page.tsx, hacen el fetch inicial) y Server Actions ("use server", en lib/actions/*.ts) que validan con Zod antes de tocar la base de datos.

Supabase

Postgres con Row Level Security activa en cada tabla: filtra qué filas ve/edita cada quien según rol_actual(), y triggers que protegen campos puntuales (como el documento).

El patrón general de cualquier acción

  participant UI as Navegador
  participant Proxy as proxy.ts
  participant SC as Server Component
  participant SA as Server Action
  participant Zod as Validación Zod
  participant RLS as Postgres + RLS
  participant Trig as Triggers

  rect rgba(79, 70, 229, 0.06)
  Note over UI,RLS: Carga inicial de la página
  UI->>Proxy: solicita /dashboard/...
  Proxy->>Proxy: verifica sesión y rol
  Proxy->>SC: permite el paso
  SC->>RLS: fetch inicial
  RLS-->>SC: filas ya filtradas por rol
  SC-->>UI: HTML renderizado
  end

  rect rgba(180, 83, 9, 0.06)
  Note over UI,RLS: El usuario hace clic o envía un formulario
  UI->>SA: llama a la Server Action
  SA->>Zod: valida los datos recibidos
  Zod-->>SA: ok, o lista de errores
  SA-->>UI: si hay errores, los muestra y se detiene aquí
  SA->>RLS: query o mutación (con los datos válidos)
  RLS->>Trig: verifica columnas protegidas
  Trig-->>RLS: permite o rechaza
  RLS-->>SA: resultado (datos o error)
  SA->>SC: revalidatePath()
  SC->>RLS: vuelve a consultar todo
  RLS-->>SC: datos frescos
  SC-->>UI: UI actualizada
  end

El paso revalidatePath() es el que más sorprende a quien recién aprende: después de que la Server Action guarda el cambio, no actualiza la pantalla ella misma — le dice a Next.js "los datos de esta ruta cambiaron", y es el Server Component quien vuelve a consultar todo y manda una versión nueva de la interfaz. El navegador nunca sabe cómo se guardó nada; solo recibe la pantalla ya actualizada.

Ejemplo real: una solicitud de matrícula

El mismo patrón, pero siguiendo un dato concreto — y con un giro interesante: dos personas distintas tocan la misma fila de la tabla matriculas en momentos distintos. 

sequenceDiagram
  actor Acu as Acudiente
  participant SA1 as crearSolicitudMatricula()
  participant DB as matriculas (RLS)
  actor Adm as Admin
  participant SA2 as actualizarEstadoMatricula()

  Acu->>SA1: clic en "Solicitar matrícula"
  SA1->>DB: insert con estado = 'Pendiente'
  alt no cumple la política RLS (otro estudiante, u otro estado)
    DB-->>SA1: rechazado por la base de datos
    SA1-->>Acu: error
  else cumple la política
    DB-->>SA1: fila creada
    SA1-->>Acu: "Solicitud enviada"
  end

  Note over DB,Adm: Aparece un badge ámbar en el sidebar del admin

  Adm->>DB: abre Matrículas, ve la fila resaltada
  Adm->>SA2: cambia el estado a "Activa"
  SA2->>DB: revisa el cupo del grupo otra vez
  alt sin cupo disponible
    DB-->>SA2: no se puede aprobar
    SA2-->>Adm: error
  else hay cupo
    DB-->>SA2: estado_matricula = 'Activa'
    SA2-->>Adm: "Estado actualizado"
  end

  Note over Acu: La próxima vez que entra, ve su matrícula "Activa"

Fíjate en el paso C: la regla "solo puedes crear tu propia matrícula, y solo en Pendiente" no vive en el formulario ni en el botón — vive en una política RLS dentro de la base de datos. Aunque alguien se salte la interfaz por completo y mande la petición a mano, Postgres la rechaza igual. Eso es lo que probamos con curl cuando construimos esta función: intentar insertar en "Activa" directamente falla con row-level security policy, sin llegar nunca a tocar la tabla.
